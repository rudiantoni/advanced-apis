# v0.0.5 (Phase 5): API security layer

After [Phase 4](v0.0.4.md) (Postgres + JPA), the API has no authentication or authorization. Phase 5 adds a **security layer** so that non-public routes are rejected before they reach controllers.

Phase 5 is not a single implementation path. The documents **v0.0.5a**, **v0.0.5b**, and future **v0.0.5x** variants are **different approaches** to the same concern: protecting the API. Each subsection is self-contained — choose **one** approach and follow only that guide. They do not stack on top of each other.

## What every approach shares

Regardless of which subsection you pick, the security layer follows the same overall shape:

1. **Configuration** - `app.security.*` in `application.yml` (or environment), loaded at startup into `AppProperties` via `AppConfig`.
2. **Public routes** - servlet paths matching regexes in `app.security.public-routes` skip the security check (for example `/open/**` and, where applicable, login or registration endpoints).
3. **Servlet filter** - a custom `OncePerRequestFilter` decides whether the request may proceed; missing or invalid credentials return `401 Unauthorized` with body `{"message":"Unauthorized"}`.
4. **Spring Security** - stateless session, CSRF disabled, `permitAll()` at the authorization layer; enforcement lives in the custom filter, registered before `UsernamePasswordAuthenticationFilter`.
5. **Phase 0 placeholders** - `AppConsts`, `AppProperties`, and `AppConfig` move from stubs to real security-related values.

Implementing two subsections in the same codebase (for example API key **and** JWT filters both active) is out of scope for these guides and requires a deliberate merge not documented here.

## Subsections (pick one)

| Doc | Approach | Summary |
|-----|----------|---------|
| [v0.0.5a](v0.0.5a.md) | **API key** | Shared secret in header `X-API-Key`; no login endpoint; clients send the same key on every protected request. |
| [v0.0.5b](v0.0.5b.md) | **JWT (basic, mock login)** | `POST /auth/login` with fixed mock credentials returns a Bearer token; `GET /users/me` reads claims from the token; protected routes require `Authorization: Bearer <token>`; no roles, no database user lookup. |

Future **v0.0.5x** documents may add other approaches (for example JWT with database-backed users or role-based access). Each new file should be treated as another alternative at the same phase level, not a mandatory next step after 5a or 5b.

## How to use this folder

1. Complete Phase 4 and confirm the API runs against Postgres.
2. Read this page and choose the approach that fits your learning or product goal.
3. Open the matching guide (**v0.0.5a**, **v0.0.5b**, or another subsection) and implement it end to end.
4. Ignore the other Phase 5 subsections unless you switch approach (typically on a branch or clean checkout).
