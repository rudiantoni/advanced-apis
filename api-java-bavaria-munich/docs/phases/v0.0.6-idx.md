# v0.0.6-idx (Phase 6 index): API security layer

Adds a **security layer** so that non-public requests are rejected before they reach controllers.

## Prerequisites

Complete every **prior** guide in filename order through the phase where **shared utilities** were added (`JsonUtil`, `AppConfig.initializeJsonUtil()`). The API must still run against **Postgres** (introduced in the phase where JPA replaced in-memory storage). Read this index before implementing any security sub-phase below.

## Sub-phases for this phase (pick one)

The **security phase** uses **parallel alternatives**, not a chain: after the prerequisites above, implement **exactly one** of Sub-Phase **6a**, Sub-Phase **6b**, or Sub-Phase **6c**. They do not stack on each other.

| Sub-Phase | Approach | Summary |
|-----------|----------|---------|
| 6a | **API key** | Shared secret in header `X-API-Key`; no login endpoint; clients send the same key on every protected request. |
| 6b | **Basic JWT, in-memory credentials** | JWT Bearer auth; `POST /auth/login` validates against `default-users` in configuration only; BCrypt password hashing; `GET /users/me` from token claims; no database user lookup or user persistence. |
| 6c | **Hybrid JWT, in-memory + database** | JWT Bearer auth; hybrid login (`default-users` first, then Postgres); public `POST /users`; BCrypt password hashing; standalone guide. |

Future security sub-phase documents may add other approaches (for example roles). Each is another alternative under the security phase, not a mandatory follow-up after 6a, 6b, or 6c.

## What every approach shares

Regardless of which sub-phase you pick, the security layer follows the same overall shape:

1. **Dependencies** - `spring-boot-starter-security` is added here (there is no security dependency before this). It is introduced together with the custom auth filter and `SecurityConfig` in the sub-phase guide you pick.
2. **Configuration** - `app.security.*` in `application.yml` (or environment), read at startup. `spring.autoconfigure.exclude` drops the default in-memory user auto-configuration when Spring Security is first added, so the custom filter chain owns authentication.
3. **Public routes** - entries in `app.security.public-routes` as a **JSON array of objects** stored as a YAML **string** (not a native YAML list). Each object has a `route` regex and an optional `methods` list. When `methods` is omitted or empty, every HTTP method on a matching path is public; when present, only those methods are public on that path.
   - It is recommended to use the folded block scalar `>-` notation since it keeps the JSON readable. Line breaks fold to spaces and Spring still receives one parseable string. You can still use raw strings (for example when using environment variables) where block scalars are impractical.
4. **Holders** - **Scaffold-phase** placeholders in `AppConsts` (`MY_CONST`) and `AppProperties` (`myProperty`) are **replaced** by the sub-phase you pick. `AppConfig` was already replaced in the **shared-utilities phase**; each sub-phase **extends** it with `initializeProperties()`. Security property parsing uses the injected Spring `ObjectMapper` directly, not `JsonUtil`, to avoid coupling the configuration class that bootstraps `JsonUtil` to that util.
5. **`PublicRouteDefinition` / `PublicRouteRule`** - configuration DTO (`definition` package) and compiled matcher (`auth` package; path regex + optional HTTP methods).
6. **`AppBeansConfig`** - separate `@Configuration` with `@DependsOn("appConfig")` that exposes a `publicRouteRules` bean for the filter. JWT sub-phases **6b** and **6c** also register a `PasswordEncoder` bean (`BCryptPasswordEncoder`) for `PasswordService`.
7. **Servlet filter** - a custom `OncePerRequestFilter` uses `publicRouteRules` to skip public requests, validates credentials on protected requests, and returns `401 Unauthorized` with body `{"message":"Unauthorized"}` when validation fails.
8. **Spring Security** - stateless session, CSRF disabled, `permitAll()` at the authorization layer; enforcement lives in the custom filter, registered before `UsernamePasswordAuthenticationFilter` (used only to anchor filter order, not for application login).

JWT-specific libraries and login endpoints belong in Sub-Phase **6b** and **6c** guides only, not in **6a**.

Implementing two sub-phases in the same codebase (for example API key **and** JWT filters both active) is out of scope for these guides and requires a deliberate merge not documented here.

## How to proceed

1. Confirm prerequisites above.
2. Choose one row from the sub-phase table.
3. Implement that sub-phase end to end.
4. Ignore the other security sub-phase guides unless you switch approach (typically on a branch or clean checkout).
