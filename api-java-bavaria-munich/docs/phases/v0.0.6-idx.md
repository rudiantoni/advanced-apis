# v0.0.6-idx (Phase 6 index): API security layer

Adds a **security layer** so that non-public requests are rejected before they reach controllers.

## Prerequisites

Complete every **prior** guide in filename order through the phase where **shared utilities** were added (`JsonUtil`, `AppConfig.initializeJsonUtil()`). The API must still run against **Postgres** (introduced in the phase where JPA replaced in-memory storage). Read this index before implementing any Sub-Phase 6x below.

## Sub-phases for this phase (pick one)

Phase 6 uses **parallel alternatives**, not a chain: after the prerequisites above, implement **exactly one** of Sub-Phase 6a, Sub-Phase 6b, or a future Sub-Phase 6x. They do not stack on each other. Other phases in this folder may use a different sub-phase model (for example incremental Sub-Phase xb on Sub-Phase xa); that is declared in each phase index.

| Sub-Phase | Approach | Summary |
|-----------|----------|---------|
| 6a | **API key** | Shared secret in header `X-API-Key`; no login endpoint; clients send the same key on every protected request. |
| 6b | **JWT (basic, mock login)** | `POST /auth/login` with fixed mock credentials returns a Bearer token; `GET /users/me` reads claims from the token; protected routes require `Authorization: Bearer <token>`; no roles, no database user lookup. |

Future Sub-Phase 6x documents may add other approaches (for example JWT with database-backed users). Each is another alternative under Phase 6, not a mandatory follow-up after 6a or 6b.

## What every approach shares

Regardless of which sub-phase you pick, the security layer follows the same overall shape:

1. **Dependencies** — `spring-boot-starter-security` is added here (there is no security dependency before this). Sub-phase guides may add further libraries (for example JWT support in Sub-Phase 6b).
2. **Configuration** — `app.security.*` in `application.yml` (or environment), read at startup. `spring.autoconfigure.exclude` drops the default in-memory user auto-configuration so the custom filter chain owns authentication.
3. **Public routes** — entries in `app.security.public-routes` as a **JSON array of objects** stored as a YAML **string** (not a native YAML list). Each object has a `route` regex and an optional `methods` list. When `methods` is omitted or empty, every HTTP method on a matching path is public; when present, only those methods are public on that path.
   - It is recommended to use the folded block scalar `>-` notation since it keeps the JSON readable. line breaks fold to spaces and Spring still receives one parseable string. You can still use raw strings (for example when using environment variables) where block scalars are impractical.
4. **Holders** — Config placeholders from the scaffold phase gain real security fields. `AppConfig` is extended with `initializeProperties()`; security property parsing uses the injected Spring `ObjectMapper` directly, not `JsonUtil`, to avoid coupling the configuration class that bootstraps `JsonUtil` to that util.
5. **`PublicRouteDefinition` / `PublicRouteRule`** — configuration DTO and compiled matcher (path regex + optional HTTP methods).
6. **`AppBeansConfig`** — separate `@Configuration` with `@DependsOn("appConfig")` that exposes a `publicRouteRules` bean for the filter.
7. **Servlet filter** — a custom `OncePerRequestFilter` uses `publicRouteRules` to skip public requests, validates credentials on protected requests, and returns `401 Unauthorized` with body `{"message":"Unauthorized"}` when validation fails.
8. **Spring Security** — stateless session, CSRF disabled, `permitAll()` at the authorization layer; enforcement lives in the custom filter, registered before `UsernamePasswordAuthenticationFilter`.

Implementing two sub-phases in the same codebase (for example API key **and** JWT filters both active) is out of scope for these guides and requires a deliberate merge not documented here.

2. Choose one row from the sub-phase table.
3. Implement that sub-phase end to end.
4. Ignore the other Sub-Phase 6x guides unless you switch approach (typically on a branch or clean checkout).
